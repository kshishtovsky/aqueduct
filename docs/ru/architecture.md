# Объяснение: Архитектура и модель памяти (v1.6.0)

В данном документе описаны архитектурные принципы, Data-Oriented Design (DoD), механизмы безопасности и стратегии управления памятью с нулевыми аллокациями в Aqueduct.

---

## 1. Почему QUIC вместо TCP?

Традиционные брокеры на TCP страдают от проблемы Head-of-Line (HoL) blocking при мультиплексировании топиков в одном соединении. Потеря одного пакета останавливает передачу для всех топиков.

Aqueduct использует **QUIC** (`quic-go`):
- **Изоляция на уровне стримов**: Потеря пакетов в одном топике не блокирует другие топики.
- **0-RTT Resumption**: Устраняет задержки TLS при повторных подключениях.
- **Транспорт UDP**: Снижает задержки ядра ОС.

---

## 2. Structure of Arrays (SoA) и Асинхронный Fan-Out

Aqueduct использует схему **Structure of Arrays (SoA)** с неблокирующими каналами и Writer-горутинами на каждого подписчика:

```go
type Router struct {
    mu sync.RWMutex

    // Плоские параллельные массивы SoA
    streamIDs []uint32               // Stream ID подписчиков
    streams   []*quic.Stream         // Указатели на QUIC-стримы
    topics    []string               // Имена топиков
    active    []bool                 // Флаги активности
    queues    []chan *MessageRef     // Кольцевые каналы очереди
    cancels   []context.CancelFunc   // Хэндлы отмены горутин

    topicIndex   map[uint64][]int    // Составной FNV-1a хэш топика
    wildcardSubs []WildcardSub       // Паттерны Wildcard (+ и #)
}
```

 При публикации брокер неблокирующе помещает `MessageRef` в очереди за наносекунды. Выделенные Writer-горутины считывают данные из очередей и отправляют их в сеть, изолируя издателя от медленных потребителей.

## 3. Атомарный подсчет ссылок (`MessageRef`)

Безопасное переиспользование буферов в `sync.Pool` без гонок данных:

```go
type MessageRef struct {
    buf       *[]byte
    ref       atomic.Int32
    expiresAt int64 // unix nano, 0 = бессрочно
}
```

- Вызов `AcquireMessageRef` создает обертку с `ref = 1`.
- Для каждого подписчика `Retain()` увеличивает `ref`.
- Каждая Writer-горутина после отправки в сеть вызывает `Release()`.
- При `ref.Add(-1) == 0` буфер возвращается в `protocol.ReleaseBuffer`, а `MessageRef` — в `msgRefPool` (**`0 allocs/op`**).

---

## 4. Wildcard Topic Matching без аллокаций

- `+` совпадает с одним сегментом топика между `/`.
- `#` совпадает со всеми последующими сегментами.
- `MatchWildcard(pattern, topic []byte)` работает за **50.41 ns/op** при **`0 allocs/op`**.

---

## 5. Архитектура безопасности (mTLS, FNV-1a ACL, AES-GCM AAL)

1. **mTLS 1.3**: Валидация сертификатов клиентов по пулу `client_ca_file`.
2. **Некоммутативный ACL**: Хэширование `FNV1a(clientID + ":" + topic)` исключает подбор и обход прав доступа.
3. **AES-256-GCM AAL и Replay**: Шифрование журналов с 12-байтным Nonce (4-байтовый случайный префикс сессии) и 4-байтовым заголовком длины. Восстановление состояния (Replay) выполняется до открытия UDP-порта.

## 6. Direct Mesh Clustering (P2P Federation)

Aqueduct поддерживает формирование кластера из брокеров, соединённых через прямую P2P QUIC-сеть. Центральный координатор или консенсус (Raft/Paxos) отсутствует — пересылка сообщений работает по принципу fire-and-forget.

### PeerManager

Каждый брокер поддерживает исходящие QUIC-соединения к статическому списку пиров. PeerManager:
- Устанавливает соединение к каждому пиру при старте с использованием mTLS 1.3
- Запускает фоновый цикл переподключения с экспоненциальной задержкой при разрыве
- Предоставляет метод `Forward()` для zero-copy пересылки фреймов всем подключённым пирам

### MeshForwarded Bit

Один бит в Command-байте протокола (бит 7, маска `0x80`) помечает фрейм как уже пересланный. Получающие пиры проверяют этот бит и пропускают повторную пересылку, предотвращая широковещательные штормы в многоузловой топологии.

### Zero-Copy Forwarding

Метод `Forward()` устанавливает MeshForwarded-бит на месте в общем буфере (0 аллокаций в куче, 0 allocs/op) и записывает модифицированный фрейм напрямую в QUIC-поток каждого пира.

### Интеграция с Router

При обработке локального сообщения в `Router.Publish()`:
1. Сообщение доставляется локальным подписчикам через SoA fan-out
2. Вызывается `PeerManager.Forward()` для отправки всем пирам
3. Получающий пир вызывает `Router.PublishFromPeer()`, который диспатчит только локально (без повторной пересылки)

## 7. Батчинг и коалесцированная запись

### Проблема: OS PPS лимиты

`quic.Stream.Write()` имеет высокую стоимость одного вызова (syscall, пакетизация, крипто). Отправка одного фрейма за раз ограничивает пропускную способность ∼300k RPS.

### Решение: Умный батчинг

#### 7.1 Протокольный батчинг (`CmdPublishBatch`)

Команда `0x04` упаковывает множество стандартных фреймов в плоский массив байт внутри одного QUIC-запроса:

```text
+--------------------------+
| CmdPublishBatch Frame    |
| +----------------------+ |
| | Sub-frame 1..N       | |
| +----------------------+ |
+--------------------------+
```

Под-фреймы распаковываются через `unsafe.Slice` с pointer arithmetic — каждый под-слайс указывает напрямую в буфер родительского батча (**zero-copy unpack**, `0 allocs/op`).

#### 7.2 Вложенный подсчёт ссылок (Nested RC)

1. **Parent `MessageRef`** создаётся для буфера батча (ref = 1 + кол-во фреймов)
2. **Child `MessageRef`** создаются для каждого под-фрейма через `AcquireChildMessageRef()` — каждый child хранит `frame []byte`, указывающий в буфер parent, и инкрементит ref parent
3. На `Release()`: когда child ref → 0, вызывается `parent.Release()`. Когда parent ref → 0, буфер возвращается в `sync.Pool`
4. Все операции — `atomic.Int32`, без блокировок на горячем пути

#### 7.3 Коалесцированная запись (Coalesced Writer)

Writer-горутина подписчика аккумулирует outgoing фреймы и сбрасывает их батчем при:

1. **Порог размера**: накоплено > `batch_size` (по умолчанию 64 КБ)
2. **Микро-таймер**: единый переиспользуемый `time.Timer` сбрасывается после первого фрейма и стреляет через `flush_interval` (по умолчанию 50 µs)

```yaml
broker:
  batch_size: 65536
  flush_interval: "50us"
```

#### 7.4 Бенчмарки

| Сценарий | Пропускная способность | allocs/op |
|----------|-----------------------|-----------|
| **BatchUnpack** (1000 фреймов) | 19.9 GB/s | **0** |
| **BatchPublish** (100 сообщ.) | 6.67M msg/s, 921 MB/s | **0** |
| Single vs Batch (на сообщение) | ~150 ns/msg (batch) vs ~920 ns/msg (single) | **0** |
