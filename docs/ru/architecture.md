# Объяснение: Архитектура и Модель Памяти

В этом документе объясняются архитектурные принципы, Data-Oriented Design (DoD) и подходы к работе с памятью без аллокаций.

## 1. Почему QUIC вместо TCP?

Классический TCP страдает от Head-of-Line (HoL) блокировок при мультиплексировании нескольких топиков в одном соединении. Потеря одного пакета останавливает доставку во всех топиках.

Aqueduct использует **QUIC** (`quic-go`), что обеспечивает:
- **Изоляцию на уровне стримов**: Потеря пакета в одном стриме не влияет на другие.
- **0-RTT возобновление**: Устраняет задержку TLS при повторном подключении.
- **UDP транспорт**: Снижает задержки ядра ОС.

## 2. Structure of Arrays (SoA) Роутер

Классический подход в Go хранит подписчиков в map'ах с указателями: `map[string][]*Subscriber`, что приводит к промахам кэша L1/L2 процессора.

Aqueduct использует **Structure of Arrays (SoA)**:

```go
type Router struct {
    mu sync.RWMutex

    // SoA плоские параллельные слайсы
    streamIDs []uint32       // Идентификаторы стримов
    streams   []*quic.Stream // Указатели на QUIC стримы
    topics    []string       // Названия топиков
    active    []bool         // Флаги активности

    topicIndex map[string][]int
}
```

При веерной рассылке сообщений брокер последовательно итерируется по плоскому массиву памяти (`streams[idx]`), что оптимально утилизирует CPU prefetcher и кэш L1/L2.

## 3. Стратегия Zero-Allocation

1. **Пул буферов**: Каждая горутина чтения получает срез байт фиксированной емкости из `sync.Pool`.
2. **Парсинг через указатели**: Заголовки разбираются напрямую из срезов байт без создания дополнительных объектов.
3. **Синхронный AAL**: При включении AAL фреймы пишутся в Page Cache ОС через `os.File.Write` напрямую из сетевого буфера, обеспечивая `0 allocs/op`.
